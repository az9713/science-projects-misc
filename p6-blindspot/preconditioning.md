# Preconditioning — P6 Blind-Spot Pass

## Topic stack

Preconditioning sits inside Krylov subspace methods, which sit inside iterative solvers for `Ax = b`, which sit inside numerical linear algebra as a whole. The stack, bottom to top:

1. **Direct factorization** (LU, Cholesky, QR) — exact in exact arithmetic, but O(n^3) work and O(n^2) fill for dense problems; infeasible for large sparse systems from PDE discretizations.
2. **Stationary iterations** (Jacobi, Gauss-Seidel, SOR) — the historical starting point, convergence governed by the spectral radius of an iteration matrix.
3. **Krylov subspace methods** (CG, GMRES, BiCGSTAB, MINRES, QMR) — build an approximate solution from `{b, Ab, A^2 b, ...}`, convergence governed by the spectrum (SPD case: condition number; nonsymmetric case: eigenvalue clustering, field of values, or pseudospectra).
4. **Preconditioning** — replace `Ax=b` with an equivalent system that has a more favorable spectrum for the Krylov method to work on, without changing the solution.
5. **Preconditioner families**, each trading setup cost against per-iteration cost against iteration count against parallel scalability:
   - Stationary iterations reused as preconditioners (Jacobi, Gauss-Seidel, SOR, SSOR).
   - Incomplete factorizations (ILU(0), ILU(k), ILUT, incomplete Cholesky).
   - Sparse approximate inverses (SPAI, FSAI).
   - Multigrid (geometric and algebraic).
   - Domain decomposition (additive/multiplicative Schwarz, FETI, BDDC).
   - Block and Schur-complement preconditioners for saddle-point systems (Stokes, mixed FEM, KKT systems).
   - Physics-based preconditioners (e.g., using a simplified or linearized physical model as the preconditioning operator).
6. **The design target above all of these**: mesh-independent convergence — the iteration count should stay roughly flat as the discretization is refined, not grow with problem size. Multigrid and (well-tuned) domain decomposition achieve this; plain ILU and Jacobi generally do not.

## Unknown unknowns

These are the things people studying this topic for the first time usually do not know they need to ask.

- **"Preconditioning" is not one operation, it is three, and they change different objects.** Left preconditioning solves `M^{-1}Ax = M^{-1}b`; right preconditioning solves `AM^{-1}u = b` with `x = M^{-1}u`; split preconditioning solves `M_1^{-1} A M_2^{-1} u = M_1^{-1} b` with `M = M_1 M_2`. Each changes which residual the Krylov method actually minimizes at each step, which matters directly for GMRES (see Misconception 2 below) and for how you must compute a stopping criterion.
- **The preconditioner does not need to be a fixed matrix.** It can itself be an inner iterative solve (e.g., one AMG V-cycle, or a few steps of Gauss-Seidel), in which case the outer method must be a "flexible" variant (FGMRES, flexible CG) because the effective preconditioning operator changes slightly from one outer iteration to the next.
- **A preconditioner that reduces the condition number is not automatically a good preconditioner.** For nonsymmetric problems, GMRES convergence is not controlled by condition number alone — eigenvalue clustering and non-normality matter, and a preconditioner can shrink the condition number while leaving convergence slow, or leave the condition number huge while clustering eigenvalues enough for fast convergence.
- **Incomplete factorizations can fail outright, not just converge slowly.** ILU(0) can produce a zero or negative pivot on an indefinite or non-diagonally-dominant matrix, and the factorization simply breaks down — this is a distinct failure mode from "many iterations needed."
- **Setup cost, application cost, and iteration count are three separate currencies, and the right preconditioner depends on which one is scarce.** A preconditioner that costs a lot to build (AMG) but is cheap to apply and drives iteration count to near-constant is right for a problem solved once at large scale; a preconditioner that is nearly free to build (Jacobi) but leaves iteration count growing is right for something solved thousands of times at small scale.
- **Multigrid convergence is not "for free" outside the elliptic, symmetric, well-resolved regime it was designed for.** For convection-dominated, highly anisotropic, or jump-coefficient problems, standard AMG/geometric multigrid can lose mesh independence unless the smoother, coarsening, or transfer operators are matched to the physics.
- **Saddle-point systems (Stokes-type, KKT systems) are indefinite, and most "black-box" preconditioners for SPD systems do not apply.** They need dedicated block or Schur-complement constructions, and the Schur complement itself is usually never assembled — it is only approximated because it is dense even when the original blocks are sparse.
- **Parallel scalability of a preconditioner is a separate axis from its serial iteration count.** One-level Schwarz methods are trivially parallel but lose mesh independence as subdomain count grows; two-level Schwarz, FETI, and BDDC restore mesh independence by adding a coarse "communication" problem that itself becomes a scalability bottleneck at very large core counts.

## Common misconceptions

Each entry gives the wrong belief, the corrected statement, and a concrete, checkable fact — two of these are backed by numpy/scipy runs done in this pass, with the real printed output included.

**1. "A diagonal (Jacobi) preconditioner fixes ill-conditioning."**
Correct statement: Jacobi (diagonal) preconditioning removes ill-conditioning that comes from bad *scaling* of rows/columns (unbalanced units or magnitudes), but does essentially nothing for ill-conditioning that comes from the *structure* of the operator itself, such as the mesh-size-dependent conditioning of a discretized Laplacian.
Check (numpy, real output): for a 1D Poisson matrix of size 50 (tridiagonal, diagonal 2, off-diagonal −1), `cond(A) = 1.053e+03` and after Jacobi scaling `cond(D^{-1}A) = 1.053e+03` — a ratio of `1.0000`, i.e. no improvement, because the matrix was already well-scaled and its ill-conditioning is structural (it grows as O(n^2) with mesh refinement). Taking the same matrix and rescaling rows/columns by factors `10^(i mod 5)` (a pure scaling distortion, same underlying problem) gives `cond(A) = 1.075e+10`, and Jacobi preconditioning cuts that roughly in half to `cond ≈ 5.324e+09` in this run — still large, but the point is qualitative: Jacobi's benefit is scaling-dependent, and for the *structural* Poisson case it did nothing at all.

**2. "GMRES's residual norm always means the true residual ‖b − Ax‖."**
Correct statement: with left preconditioning, GMRES minimizes and reports the norm of the *preconditioned* residual `‖M^{-1}(b − Ax)‖`, not `‖b − Ax‖` itself. If `M` is badly scaled, the two can differ by orders of magnitude, and a solver that reports "converged" can leave a much larger true residual than the requested tolerance suggests.
Check (numpy/scipy, real output): solving a 40×40 random diagonally-dominant nonsymmetric system with a deliberately badly-scaled left preconditioner (one diagonal entry scaled by `1e-4`), GMRES with `rtol=1e-8` reported a final preconditioned relative residual of `8.095e-12`, while the actual true relative residual `‖b − Ax‖/‖b‖` computed after solving was `7.236e-09` — about 894 times larger than what the solver reported (`info=0`, 38 iterations, exact multiplier in this run: `8.939e+02`). Right preconditioning does not have this problem, because the residual `b − Au` for the transformed system is identical to `b − Ax` for the original one — this is the practical reason many production codes default to right preconditioning when the true residual matters for the stopping test.

**3. "ILU(0) always exists and just gives a slower version of full LU."**
Correct statement: ILU(0) can break down with a zero or negative pivot on matrices that are not (diagonally dominant and irreducible, or M-matrices, or SPD after a compatible ordering); when it does not break down outright, its quality still degrades sharply on strongly indefinite or highly nonsymmetric matrices, sometimes producing a preconditioned system that converges more slowly than no preconditioning at all.
Check: this is a textbook-verifiable fact (Saad, *Iterative Methods for Sparse Linear Systems*, ILU existence theorems restricted to M-matrices/diagonally-dominant matrices) rather than one worth spending a numpy run on; the fast way to check it on any concrete matrix is to run the factorization and watch for a pivot with magnitude near or below machine epsilon relative to the matrix norm — most sparse libraries (e.g., SuperLU, `scipy.sparse.linalg.spilu`) raise or warn on this rather than silently returning garbage.

**4. "Multigrid is 'the' fast preconditioner; reach for it whenever CG/GMRES converges slowly."**
Correct statement: multigrid's mesh-independent, near-linear-cost convergence is a *design property tied to smooth-error assumptions* (an elliptic-type operator whose high-frequency error components are damped by a cheap smoother, and whose low-frequency components live in a coarser space that a Galerkin coarse-grid operator represents well). Convection-dominated, highly anisotropic, or strongly heterogeneous-coefficient problems violate these assumptions and need matched smoothers/coarsening (e.g., line smoothers for anisotropy, AMG strength-of-connection tuning for jumps) or multigrid underperforms plain ILU.
Check: this is a qualitative, not-numerically-quick-to-demonstrate fact about smoother/operator matching; the check to run in practice is to plot iteration count against mesh refinement for the specific problem — flat is mesh-independent, growing means the smoother/coarsening choice does not match the physics, not that "multigrid doesn't work."

**5. "A tighter drop tolerance in ILUT (more fill-in) always means fewer Krylov iterations."**
Correct statement: iteration count as a function of fill-in is usually monotone but *not linear*, and past a certain fill level the marginal iteration-count reduction is far smaller than the added setup and per-application cost — the optimal operating point (measured in total wall-clock time, not iteration count) is often at a fairly loose drop tolerance, not the tightest one that still fits in memory.
Check: this is confirmed empirically in nearly every ILUT benchmarking study (e.g., Saad's ILUT papers) by plotting total solve time, not iteration count, against fill level — the curve is typically U-shaped, and iteration count alone hides this because it ignores the cost per application.

## Rat-holes

Places that consume disproportionate time relative to the insight gained, for someone building working intuition rather than writing a new preconditioner from scratch:

- **Deriving the full algebraic multigrid coarsening algorithm (classical Ruge-Stüben) from first principles.** The strength-of-connection heuristics and C/F-splitting rules are intricate and mostly matter for implementers, not for someone who needs to use AMG as a preconditioner and understand its convergence behavior.
- **Memorizing the exact fill patterns of ILU(k) for k > 1.** The qualitative trade-off (more fill, better approximation of A^{-1}, higher setup/apply cost, possible loss of sparsity benefit) is the transferable fact; the precise level-k fill graph algorithm is an implementation detail.
- **Working through FETI/BDDC's full mathematical equivalence proof.** Useful for someone implementing a domain-decomposition library; for most purposes it is enough to know that FETI and BDDC are dual/primal formulations of the same two-level substructuring idea, both achieving mesh- and subdomain-count-independent convergence via a coarse problem.
- **Hand-deriving the exact spectral equivalence constants for a given SSOR or SPAI preconditioner.** These constants exist and matter for a convergence-rate proof, but the practical decision of "does this preconditioner help enough to justify its cost" is made empirically (measure iterations and wall-clock time), not by deriving the constant.
- **Chasing the "optimal" relaxation parameter ω in SOR.** It has a closed form only for special matrix classes (consistently ordered matrices, e.g. certain discretized Poisson problems); for general sparse matrices from real applications this parameter search is rarely worth the time compared to switching to ILU or multigrid entirely.

## High-yield study prompts

1. Derive, by hand, why left, right, and split preconditioning all solve the same underlying linear system for `x` but minimize different residual quantities during a GMRES iteration — write out `M^{-1}(b-Ax)` versus `b-Ax` for a small 3×3 example and confirm numerically that GMRES with a bad left preconditioner can report a much smaller residual than the true one, then repeat with right preconditioning.
2. Take a 2D discretized Poisson matrix, run CG with no preconditioner, with Jacobi, and with incomplete Cholesky, and plot iteration count versus mesh size (e.g., n = 20, 40, 80, 160) for each; identify which preconditioner(s) hold iteration count roughly flat (mesh-independent) and which show growth, and explain why in terms of the preconditioner's spectral effect.
3. Deliberately construct a matrix on which ILU(0) breaks down (a negative or zero pivot) — an indefinite or non-diagonally-dominant sparse matrix is enough — and observe the failure directly (either an exception from `scipy.sparse.linalg.spilu` or a corrupted factorization); then show that adding a small diagonal shift or reordering (e.g., a Krylov-space "Manteuffel shift" style perturbation) restores existence.
4. Build a simple saddle-point system (e.g., a 2D Stokes-type block system with a zero (2,2) block) and implement a block-diagonal preconditioner using an approximate Schur complement; measure how iteration count for a Krylov method like MINRES changes as the Schur-complement approximation is made cheaper (more approximate) versus more exact (more expensive), quantifying the setup/apply/iteration-count trade-off directly.
5. Compare one-level additive Schwarz to a two-level version (adding a coarse-grid correction) on a domain split into an increasing number of subdomains (e.g., 4, 16, 64), and measure whether iteration count stays flat or grows with subdomain count in each case — this is the direct, hands-on way to see why a coarse space is necessary for parallel scalability, not just an optional refinement.
6. Read Saad's ILU existence theorem statement (M-matrices / diagonally dominant matrices) and identify, for three matrices you construct yourself, which satisfy the hypothesis and which do not, before running the factorization to confirm the prediction — this converts the "does ILU exist" question from an empirical guess into a checkable structural property.
7. For a specific physical PDE you already know (e.g., convection-diffusion), design a "physics-based" preconditioner (e.g., an operator that solves the diffusion-only part exactly, or a semi-implicit splitting), and compare its iteration count and per-application cost against a generic algebraic preconditioner (ILU or AMG) on the same discretized system — this is the fastest route to understanding why physics-based preconditioning can beat black-box methods when the black-box assumptions (elliptic, symmetric, well-scaled) do not hold.
