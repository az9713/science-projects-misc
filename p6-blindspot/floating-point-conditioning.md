# Blind-Spot Pass: Floating Point, Conditioning, and Backward Stability

## Topic Stack

This topic has four layers, and most confusion comes from mixing them up.

1. **Representation layer.** IEEE 754 binary formats: binary16 (half, 1 sign + 5 exponent + 10 mantissa bits), bfloat16 (1 + 8 + 7, same exponent range as binary32 but far less mantissa precision), binary32 (single, 1 + 8 + 23), binary64 (double, 1 + 11 + 52). Each format has a unit roundoff u — the largest relative error from rounding one representable value to the nearest representable value, u = 2^-53 for binary64. Formats also define subnormals (denormals), which fill the gap between zero and the smallest normal number at the cost of precision, and multiple rounding modes (round-to-nearest-even is the default; round toward zero, +inf, -inf also exist).

2. **Arithmetic layer.** The standard model: for a basic operation op in {+, -, *, /}, the computed result fl(x op y) satisfies fl(x op y) = (x op y)(1 + delta) with |delta| <= u. This is the single most load-bearing fact in the whole subject — nearly every stability proof reduces to chaining these (1 + delta) factors through a sequence of operations.

3. **Problem layer.** Every numerical problem has a condition number: a measure of how much the exact answer moves when the input is perturbed by a tiny relative amount, independent of any algorithm. For a linear system Ax = b, kappa(A) = ||A|| ||A^-1||. Least squares, eigenvalue, and singular value problems each have their own (related but distinct) condition numbers, and these can differ sharply from kappa(A) of a coefficient matrix that happens to appear in the problem.

4. **Algorithm layer.** Backward error and forward error are properties of a specific algorithm run on a specific problem instance. Backward stability is the standard: an algorithm is backward stable if the computed answer is the exact answer to a slightly perturbed input problem, where "slightly" means a relative perturbation on the order of u times a modest constant. The link between layers 3 and 4 is the rule of thumb: forward error <= condition number x backward error (roughly; the precise statement is an inequality with a problem-dependent constant, not an identity).

A priori bounds are derived by hand once, before running the algorithm. A posteriori and running error analysis compute or bound the actual error alongside the actual computation, using quantities produced during the run itself (this is the technique behind LAPACK's error estimates and behind Higham's running error analysis in *Accuracy and Stability of Numerical Algorithms*).

## Unknown Unknowns

- **Condition number is not one number per matrix.** kappa(A) as used for "solve Ax=b" is not the same quantity as the condition number of A's eigenvalues, or of A's singular values, or of the least-squares problem min ||Ax - b||. A matrix can be well-conditioned for one of these and ill-conditioned for another. People memorize "kappa(A) = sigma_max/sigma_min" and then misapply it to eigenvalue problems, where the relevant condition number for a simple eigenvalue lambda is 1/|cos(angle between left and right eigenvectors)|, a completely different object that can be huge even when kappa(A) is small (a highly non-normal matrix).

- **bfloat16 and binary16 are not "lower-precision binary64."** They differ in exponent range, not just mantissa length. bfloat16 keeps binary32's 8-bit exponent (same overflow/underflow range as single precision) but only 7 mantissa bits, so it trades precision for range in a specific, deliberate way aimed at deep learning training dynamics. binary16 has a 5-bit exponent and overflows/underflows far earlier than either. Code tuned for numerical stability in binary64 can silently overflow in binary16 at magnitudes that look "normal."

- **Rounding mode is not a free parameter you can ignore.** Round-to-nearest-even (ties-to-even) is default and is what the standard model assumes. Round-toward-zero or directed rounding modes change the sign and magnitude of the error term and break naive assumptions that errors "average out." Interval arithmetic and some accuracy-verification techniques deliberately switch rounding mode to bound results from both sides.

- **Backward stability does not mean small forward error, and instability does not mean large forward error either — until you fold in the condition number.** A backward stable algorithm on an ill-conditioned problem can, and should, produce large forward error; that is not a bug in the algorithm. Conversely, an unstable algorithm can occasionally get lucky on a well-conditioned or structured problem and produce a small forward error, which hides the instability until a different input exposes it.

- **The standard model's "1 + delta" is a bound, not an estimate.** People often plug in u as if it were the actual expected error per operation, then are surprised when error accumulates faster (or, less often, more slowly) than n*u after n operations. The true accumulated bound typically grows like a small multiple of n*u under realistic assumptions, but the constant and the growth pattern (linear vs. worse) depend on the specific algorithm's structure, not on the standard model alone.

## Common Misconceptions

**1. "Double precision (binary64) has about 15-17 decimal digits, so results are accurate to 15-17 digits."**
Correct statement: binary64 can *represent* numbers to about 15-17 significant decimal digits, and a single operation has relative error bounded by u ~ 1.1e-16. But the *accuracy of a computed answer* depends on the problem's condition number and the algorithm's stability, and can be far worse than 15-17 digits even with every individual operation correctly rounded.
Concrete check: solving Ax = b for A = [[1,1],[1,1+1e-10]], b = [2, 2+1e-10] gives kappa(A) ~ 4.0e10 (measured: `np.linalg.cond(A)` = 39999947702.45). Perturbing b by a relative amount of about 5.0e-9 (measured: `np.linalg.norm(db)/np.linalg.norm(b)` = 4.9999999999e-09) changes the solution by a relative amount of about 200 (measured: forward error = 199.9999822414331), matching kappa(A) x backward error = 199.9997385... Sixteen digits of input precision produced roughly zero digits of output accuracy.

**2. "Catastrophic cancellation happens because subtraction is inaccurate."**
Correct statement: floating-point subtraction of two nearby representable numbers is itself exact or nearly exact (the standard model's delta still applies, bounded by u). What is "catastrophic" is that subtracting two nearly-equal numbers each carrying prior rounding error amplifies that *pre-existing* relative error into a much larger relative error in the small result, because the absolute error stays roughly the same while the result's magnitude shrinks.
Concrete check: computing f(x) = (1 - cos(x)) / x^2 at x = 1e-8 the naive way gives 0.0 (measured), because 1 - cos(1e-8) loses essentially all significant digits when cos(1e-8) rounds to a value indistinguishable from 1.0 in binary64. The mathematically equivalent, cancellation-free form f(x) = (sin(x/2) / (x/2))^2 / 2 gives 0.5 (measured), matching the true limiting value of 0.5. No individual operation violated the standard model; the algorithm choice, not the arithmetic, caused the failure.

**3. "u = 2^-53 is 'machine epsilon,' the smallest number such that 1 + eps != 1."**
Correct statement: this conflates two related but distinct constants. `np.finfo(float64).eps`, commonly called machine epsilon, equals 2^-52 (measured: 2.220446049250313e-16) — the gap between 1.0 and the next representable double. Unit roundoff u = eps/2 = 2^-53 (measured: 1.1102230246251565e-16) is the *bound on rounding error* used in the standard model, because round-to-nearest rounds to within half an ulp. The two differ by exactly a factor of 2, and papers/textbooks are not always consistent about which one they call "machine epsilon" — always check which the source means.
Concrete check: `1.0 + u/2 == 1.0` evaluates to True (u/2 rounds away entirely), `1.0 + u == 1.0` also evaluates to True (u alone still rounds down to 1.0 under round-to-nearest-even, since 1.0 + u is exactly halfway and ties go to even), but `1.0 + 1.0000001*u == 1.0` evaluates to False — the smallest amount that reliably survives rounding is just over u, not u itself, and the exact tie-breaking behavior depends on round-to-nearest-even.

**4. "An unstable algorithm always gives a wrong-looking (obviously bad) answer."**
Correct statement: an unstable algorithm can return a plausible-looking number that is wrong by many orders of relative magnitude, with no warning sign in the output itself, especially on well-scaled test inputs that happen not to trigger the instability.
Concrete check: the classic example is the naive quadratic formula (b - sqrt(b^2 - 4ac)) / 2a for a case with b >> sqrt(discriminant), where cancellation in the numerator destroys precision in one root while the other root (computed via the other sign) stays accurate — the answer looks like an ordinary floating-point number, not a NaN or an obviously absurd value, so nothing in the output flags the loss.

**5. "Ill-conditioned problem and unstable algorithm are two ways of saying the same thing."**
Correct statement: conditioning is a property of the *problem* (how much the exact answer changes for a tiny exact perturbation of the exact input), entirely independent of how you compute it — even an oracle with infinite precision faces the same sensitivity. Stability is a property of the *algorithm* (whether the computed answer is the exact answer to a nearby problem). A stable algorithm on an ill-conditioned problem still gives a large forward error, correctly, because the problem itself is sensitive; that is not an algorithm failure. An unstable algorithm on a well-conditioned problem can still give a large forward error unnecessarily, and that is an algorithm failure.
Concrete check: in the linear-system experiment above, `np.linalg.solve` (LAPACK's LU with partial pivoting, a backward stable algorithm) still produced a forward error of about 200 on the ill-conditioned A. That large forward error is expected and correct — it reflects kappa(A), not a defect in `solve`. Running an unstable method (e.g., forming and using the explicit inverse, or Gaussian elimination without pivoting on a matrix requiring pivoting) on a well-conditioned matrix, by contrast, would show large forward error that a stable method on the same matrix would not — that gap is the signature of instability, not conditioning.

## Rat-Holes

- **Chasing "the" condition number of a general nonlinear problem.** Beyond linear systems and the standard least-squares/eigenvalue/SVD cases, condition numbers require a derivative (a Jacobian-based sensitivity), and deriving them from scratch for a novel problem is a research-level side quest, not a warm-up exercise. Don't rebuild first-principles perturbation theory before checking whether a known condition number formula already covers the case.
- **Trying to get "the exact rounding error" of a multi-step computation by hand.** The standard model composes into products of (1 + delta_i) terms, and expanding these exactly is combinatorially unpleasant and not how practitioners work. The standard technique is to bound |product(1+delta_i) - 1| by n*u/(1 - n*u) (or similar), not to track individual delta_i values — attempting exact tracking is a time sink with no payoff over the standard bound.
- **Treating subnormals as a corner case to memorize the exponent bit pattern of and move on.** Subnormals matter operationally (gradual underflow prevents some algorithms from producing wrong zeros near the smallest normal number) but the bit-level encoding details rarely matter for algorithm design; time is better spent on when subnormals get flushed to zero by hardware/compiler flags (a real, silent source of divergence between environments) than on memorizing the encoding.
- **Assuming higher precision (or mixed precision / compensated summation) is a substitute for understanding conditioning.** Extra precision shrinks u but does not change kappa(A); an ill-conditioned problem run in quad precision is still ill-conditioned, just with the crossover point pushed further out. It's easy to spend a long time tuning precision instead of addressing the actual sensitivity of the problem or algorithm choice.
- **Over-indexing on Higham's book as encyclopedic reference rather than reading the relevant chapter for the problem at hand.** *Accuracy and Stability of Numerical Algorithms* is long and covers many algorithm families; reading it cover to cover before touching a specific stability question is a rat-hole — look up the chapter for the relevant operation (e.g., triangular solves, QR, least squares) instead.

## High-Yield Study Prompts

1. Derive, from the standard model fl(x op y) = (x op y)(1 + delta), the forward error bound for computing the sum of n floating-point numbers via naive left-to-right summation. State the bound in terms of n and u, and identify which step in the derivation would change if you used pairwise (recursive) summation instead.
2. Take a 2x2 or 3x3 matrix you construct to have kappa(A) around 1e8 in binary64. Solve Ax=b with `numpy.linalg.solve`, then perturb b by a relative amount of about 1e-12, and measure the actual relative change in x. Compare the measured forward error against kappa(A) x (relative perturbation in b) and note whether the rule of thumb over- or under-predicts, and by how much.
3. Implement the naive quadratic formula and a cancellation-safe variant (using the sign of b to choose which form avoids subtracting nearby quantities) in binary32. Find a coefficient triple (a, b, c) where the two implementations disagree in the smaller root by more than 1e-3 relative error, and explain which operation caused the disagreement.
4. State, precisely, the difference between the condition number of a simple eigenvalue of a non-normal matrix and kappa(A) = ||A||·||A^-1||. Construct a 2x2 non-normal matrix where the eigenvalue condition number is large while kappa(A) is close to 1, and verify numerically by perturbing an entry and comparing the eigenvalue's relative shift to both condition numbers.
5. Explain, in your own words, why a backward stable algorithm applied to an ill-conditioned problem is not a bug, using the forward-error <= condition-number x backward-error inequality. Then construct one numerical example where the forward error you observe is much smaller than the bound predicts, and explain why the bound is only an upper bound rather than an equality.
6. Write a running error analysis for the inner product of two n-vectors (accumulate the error bound alongside the sum, term by term, using the running quantities actually computed) and compare the resulting bound at n=1000 against the simple a priori bound of n*u times the sum of absolute values. State which bound is tighter and why.
7. Convert a batch of binary64 numbers to bfloat16 and separately to binary16, and find, by construction, one value that overflows in binary16 but not in bfloat16 despite bfloat16 having far fewer mantissa bits. Explain the difference in terms of exponent field width, not mantissa width.
